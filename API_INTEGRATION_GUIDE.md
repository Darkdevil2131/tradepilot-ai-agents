# API Integration Guide

Base URL locally: `http://127.0.0.1:8000`. The hosted base URL is unknown until an eligible deployment is provisioned.

All endpoints except health require `Authorization: Bearer <API_KEY>`. Keep the API key in a backend secret store; do not ship it to a browser/mobile client.

## Analyze shipment

```bash
curl -X POST http://127.0.0.1:8000/api/v1/shipments/analyze \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer YOUR_LOCAL_API_KEY' \
  --data @examples/analyze_shipment.json
```

The response includes an `agents` object with per-agent status, results and provenance. `route_optimization` values are estimates; `carrier_research` records and coverage are synthetic; quotes are user-provided; the analysis is not a booking. Quotes with different currencies are not compared by raw amount because no FX conversion is configured. When no document data is supplied, `document_intelligence` runs against empty input and returns the baseline required-document checklist.

## Retrieve saved analysis

```bash
curl http://127.0.0.1:8000/api/v1/shipments/DEMO-001 \
  -H 'Authorization: Bearer YOUR_LOCAL_API_KEY'
```

Retrieval succeeds only while the saved record remains in the configured SQLite database. A deployment with ephemeral disk can lose records.

## Validate documents

```bash
curl -X POST http://127.0.0.1:8000/api/v1/documents/validate \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer YOUR_LOCAL_API_KEY' \
  -d '{"shipment":{"origin":"Mumbai","destination":"Singapore","cargo_description":"parts","weight_kg":100,"documents":[]}}'
```

## Errors

- `401`: bearer key missing or invalid.
- `422`: invalid request shape or field values.
- `404`: no saved shipment with that ID in this database.
- `503`: server API key is not configured.
- `500`: safe generic error; details remain in server logs.

## Sample offline response shape

The specific route estimates are computed for each request. This abbreviated example shows the response structure only:

```json
{
  "shipment_id": "DEMO-001",
  "status": "completed",
  "persistence": "sqlite_ephemeral_or_local",
  "data_provenance": ["ESTIMATED", "SYNTHETIC", "USER_PROVIDED"],
  "agents": {
    "route_optimization": {"agent": "route_optimization", "status": "completed", "provenance": ["ESTIMATED"], "data": {"routes": "computed estimates"}, "warnings": []},
    "carrier_research": {"agent": "carrier_research", "status": "completed", "provenance": ["SYNTHETIC"], "data": {"carriers": "synthetic fixtures"}, "warnings": []},
    "risk_compliance": {"agent": "risk_compliance", "status": "completed", "provenance": ["USER_PROVIDED"], "data": {"live_screening": false}, "warnings": []},
    "document_intelligence": {"agent": "document_intelligence", "status": "completed", "provenance": ["USER_PROVIDED"], "data": {"valid": false, "documents_checked": 0, "missing_document_types": ["commercial_invoice", "packing_list", "bill_of_lading"]}, "warnings": []},
    "market_procurement": {"agent": "market_procurement", "status": "completed", "provenance": ["ESTIMATED"], "data": {"recommendation": "computed only from eligible submitted quotes"}, "warnings": []},
    "logistics_orchestrator": {"agent": "logistics_orchestrator", "status": "completed", "provenance": ["USER_PROVIDED"], "data": {"workflow": "LangGraph StateGraph", "bounded_attempts": 2}, "warnings": []}
  },
  "summary": "Analysis completed using deterministic offline tools. No live carrier, route, customs, or market feeds were queried."

```

OpenAPI is generated by FastAPI at `/openapi.json`; interactive docs are at `/docs`.

## Document upload and processing

Upload PDF, PNG, JPEG or TIFF files up to 10 MiB:

```bash
curl -X POST "$BASE_URL/api/v1/documents/extract" \
  -H "Authorization: Bearer $TRADEPILOT_API_KEY" \
  -F "file=@invoice.pdf;type=application/pdf"
```

Use `/api/v1/documents/process` for a background job and poll
`/api/v1/jobs/{job_id}`. The response contains extracted text/tables, OCR status,
SHA-256, visible signature/stamp indicators and PDF signature fields. The
authenticity status is intentionally `not_verified`; these indicators are not
proof of identity or document validity.

## Commercial workflow

1. `POST /api/v1/rfqs` creates a draft.
2. `POST /api/v1/rfqs/{id}/dispatch` queues internal delivery records.
3. `POST /api/v1/rfqs/{id}/responses` records an invited carrier response.
4. `POST /api/v1/approvals` records an approver's decision.
5. `POST /api/v1/bookings` creates an approval-linked dry-run booking intent.
6. `POST /api/v1/bookings/{id}/tracking` appends provenance-labelled events.
7. `POST /api/v1/purchase-orders` creates an approval-referenced draft PO.

SMTP delivery requires explicit environment configuration and an operator call
to `/api/v1/notifications/{id}/send`. External carrier booking and ERP writes
are not included and return a safe failure instead of pretending success.

## Roles and operational endpoints

Configure separate viewer, analyst, operator, approver and administrator keys.
The legacy key maps to administrator for compatibility. Administrators can read
the audit log and Prometheus-format metrics. SQLite backups are created through
the backup endpoint; PostgreSQL must use managed backups or `pg_dump` and a
verified restore procedure.

## Compare split freight and delay costs

Submit `examples/impact_comparison.json` to the shipment analysis endpoint. Read
`agents.route_optimization.data.impact_comparison`. The first portion carries
the critical weight. Each portion lists its legs, freight charges and delivery
time. Options are ranked by freight plus the cost of waiting for the critical
portion. A target date can be missed at a cost; a shipment deadline is a hard
constraint. The original Dubai–Mumbai fixture remains available. India split
scenarios use explicit bidirectional synthetic corridors for Kochi–Chennai,
Kochi–Bengaluru, Chennai–Bengaluru, Mumbai–Pune, Mumbai–Delhi,
Mumbai–Ahmedabad, Hyderabad–Bengaluru, Kolkata–Bhubaneswar,
Chennai–Visakhapatnam, and Delhi–Jaipur. Modes vary by corridor. Split plans
include road pickup and delivery, so include `road` in `allowed_modes`.
Set `closed_leg_ids` or `freight_multiplier` within `impact_scenario` to
compare disruptions and prices. Empty options include rejection reasons.
Ordinary route comparisons expose `cost_estimate_inr` on modeled India
corridors. The legacy USD field uses a fixed illustrative INR 85/USD
conversion. Quoted amounts retain their own currency. With road disabled,
ordinary air, sea, and rail options cover terminal-to-terminal movement only.
Road routes use 57 selected hubs and 70 bidirectional planning links,
including major national corridors and regional feeders. The agent can use
these linked roads even where no dedicated multimodal fixture exists.
Corridor references describe broad geography. Estimated distances, drive
times, capacities, and modeled tariffs do not verify truck access, traffic,
tolls or actual pricing. A split scenario without any connected option in the
offline model returns a blocked decision.

Send a disruption with `affected_leg_ids` set to directional IDs from
`routes[].evidence_ids` to target a road segment. The opposite direction has
its own ID. Each route option includes the chain of waypoints and its evidence
references. Coastal and rail service schedules still use synthetic fixtures.

Optional `carrier_services` entries let operators submit exact directional
lane, mode, capacity and a source reference for a real carrier quote.
For this workflow, first analyze the shipment to obtain ordered
`recommended_route.evidence_ids`. Resubmit with `carrier_services` and a quote
containing those IDs in `route_leg_ids`, a `source_reference`, `valid_until`,
`transit_hours`, `quoted_capacity_kg`, and `door_to_door_total: true`.
The result includes `market_procurement.data.quote_assessments` for the UI
to show why each offer was rejected. Check the orchestrator's
`decision.commercial_evidence` to distinguish submitted offers from demo
tariffs. If a closure changes the route, the old quote requires a new match.
Set `commercial_mode: "submitted"` for real shipments so the workflow
requires submitted evidence even while carrier offers are still outstanding.
Shipment-wide quotes cannot qualify a split shipment with separately sourced legs.
Missing contacts and history stay empty or unknown. For domestic road/rail-only
requests, submit a `consignment_note` with its number and consignee. A conflict
between raw labelled document text and explicit fields blocks validation.

## Provider geometry and road weather

Configure `TRADEPILOT_OSRM_URL` with the base of an authorized OSRM deployment
and `TRADEPILOT_FORECAST_URL` with an authorized Open-Meteo-compatible
`/v1/forecast` endpoint. Public Open-Meteo hosting limits free usage to
eligible non-commercial workloads. OSRM can be self-hosted. No default
endpoint calls are enabled. Use endpoints approved to receive shipment
coordinates. Keep both endpoints server-side.

For a road-only shipment, add `road_guidance` to the normal analysis request:

```json
{
  "origin": "Kochi",
  "destination": "Chennai",
  "cargo_description": "Machine parts",
  "weight_kg": 500,
  "allowed_modes": ["road"],
  "road_guidance": {
    "origin": {"latitude": 9.9312, "longitude": 76.2673},
    "destination": {"latitude": 13.0827, "longitude": 80.2707}
  }
}
```

Coordinates should be the actual pickup and delivery points. Optional
`road_guidance.departure_at` takes a timezone-aware timestamp and defaults to
request time. The result includes longitude/latitude route geometry, modeled
drive time, and hourly precipitation, gust, visibility and weather code at
sampled points. Sample ETAs interpolate provider segment times when available
and use distance interpolation otherwise. Forecasts use the next hour
boundary. Coverage is sampled, up to 12 points per returned
route, over the provider's configured seven-day forecast. The ranking checks
coverage, planning weather flags, supplied disruptions and deadlines before
comparing modeled transit. Critical weather flags and missing coverage
withhold the recommendation for that option. These are planning flags.

Display `provider_status`, the weather series and the orchestrator's
`route_weather` gate. Use the route ID in `evidence_ids` when binding a carrier
quote to a provider route. Reported disruptions can target that ID or the
origin/destination names. Provider mode requires submitted commercial
evidence. It does not estimate freight prices, tolls, live traffic or
truck-specific restrictions. Weather attribution: Open-Meteo. Routing
attribution: OSRM and OpenStreetMap contributors.

## Truck traffic, tolls, and restriction evidence

Add a truck profile to `road_guidance` for truck-specific routing:

```json
{
  "truck": {
    "height_cm": 350,
    "width_cm": 240,
    "length_cm": 850,
    "tare_weight_kg": 4200,
    "loaded_weight_kg": 7000,
    "gross_weight_rating_kg": 9000,
    "max_axle_weight_kg": 4000,
    "axle_count": 2
  },
  "max_toll_inr": 800
}
```

This mode uses the HERE Routing API v8 with the truck dimensions, loaded
weight, gross rating and axle data. The API requests time-aware duration
and INR toll totals. Configure `TRADEPILOT_HERE_TRUCK_ENABLED=true` and
`TRADEPILOT_HERE_API_KEY` only after confirming that the account and usage
are authorized and no-charge, including the additional toll transaction
and expected request volume. The feature is off by default.

Read `routes[].truck_evidence` for the provider duration, baseline,
time-aware delta, toll estimate and restriction notice codes. Time-aware
estimates can use live or historical traffic. Posted restrictions and toll
conditions still require operational confirmation. A missing toll stays
unknown. A reported violation, a missing comparable baseline or toll price,
or an exceeded toll budget prevents that alternative from being selected.
Other provider notices are flagged for human review. The route still goes
through the existing weather and submitted-quote checks. A toll estimate
is separate from the all-in shipment quote. Truck mode does not substitute
OSRM if the truck provider cannot supply evidence.
Carrier Research assigns synthetic leg tariffs using combined weight on each leg. See carrier_research.data.leg_plans and market_procurement.data.sourced_plan for the priced plan. Shipment-wide quotes have no leg scope and cannot replace these tariffs.

## Synthetic carrier evaluation

Submit `examples/synthetic_provider_comparison.json` to the analysis endpoint.
The lower air offer exceeds the demo carrier's capacity. Inspect
`agents.market_procurement.data.recommendation` for the eligible sea offer.
A quote must match both the carrier ID and mode on the eligible shortlist.
A high severity cargo flag holds the procurement recommendation for review.
The amounts are synthetic submitted totals. Charges omitted from an offer
are not estimated by this comparison.

Carrier reliability is the on-time fraction for the exact provider and
directional lane. With zero matching rows it is null. See
`tradepilot/fixtures/history.csv` for the evidence and
`scripts/generate_history.py` for its deterministic generator. The dataset
is development material; the workflow uses aggregation, without model training.

## Reassessment and dimensional fit

Submit a changed request with the same shipment ID. The authenticated
`GET /api/v1/shipments/{shipment_id}/history` endpoint returns ordered
revisions with the submitted inputs, changed top-level fields and full results.
Historical inputs for records created before the migration are unavailable.
Reanalysis runs the full workflow. Revisions share the local SQLite lifetime.

Optional `dimensions_cm` is a three-number bounding box for the largest
package. The fixture allows rotation across the three axes and checks each
service envelope. Missing dimensions leave fit unverified. Request rail with
`allowed_modes: ["rail"]` on the synthetic Mumbai–Delhi corridor.

## Strategic explanation

Read `agents.logistics_orchestrator.data.explanation` for the objective,
conditional conclusion, alternative cost comparisons, evidence paths,
pairwise break-even thresholds, assumptions and next actions.
The top-level summary now uses this calculated conclusion.
Sensitivity thresholds hold freight, topology, capacity and critical weight
fixed. They compare pairs of feasible options and do not imply uncertainty
estimates or prediction accuracy. All fixture-derived comparisons are synthetic.
The explanation is part of the orchestrator and requires no model call.

For shipments with several commercial invoices, provide the shipment-wide
`declared_value` and its optional three-letter `declared_value_currency`.
Validation compares the combined invoice amount with the declaration, using
the existing tolerance of 1% or one currency unit, whichever is larger.
When the declaration omits a currency, validation assumes the single invoice
currency. Mixed currencies require a common valuation.

Procurement returns each eligible quote's `includes_insurance` flag. When
eligible quotes have different coverage terms, the response retains their
prices and asks for comparable offers before recommending a carrier.


## Advanced agent decision inputs

The shipment request accepts these optional controls:

- `optimization`: non-negative `cost_weight`, `time_weight`, `risk_weight` and `reliability_weight`. At least one must be positive; the route agent normalizes them.
- `disruptions`: user-provided signals with affected modes/locations, severity, delay and provenance. Severity at or above 0.95 blocks a matched route; lower severity adjusts its time and risk.
- `supplier_offers`: price, lead time, capacity, quality, certifications, contact and provenance. Set `required_quantity` and `required_certifications` to enforce eligibility.
- `documents[].raw_text`: plain text containing explicit labels such as `Invoice Number:`, `Consignee:`, `Currency:`, `Total:` or `Package Count:`. User-supplied `fields` override extracted values.

See `examples/intelligent_shipment.json`. Scores are deterministic comparisons within the submitted candidate set. A recommendation is not a prediction, live market fact, purchase, booking or compliance clearance.
